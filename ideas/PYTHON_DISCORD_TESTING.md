# PYTHON-DISCORD — Testing mechanics

Уникальные инженерные паттерны из тестовой инфраструктуры `python-discord/bot`. Обычные unit-тесты как таковые не превращены в идеи; оставлены только переиспользуемые механики.

## PDIS-T001 — Spec-locked Discord mocks
- Тестовые объекты Discord строятся с `spec_set` реального discord.py объекта.
- Доступ к несуществующему атрибуту сразу падает `AttributeError`, поэтому опечатка в production-коде не маскируется обычным MagicMock.

## PDIS-T002 — Mock objects проходят `isinstance` как реальные Discord-типы
- Специализированные mocks можно использовать там, где код проверяет тип `discord.Member`, `Guild`, `Role`, `Context` и т. п.
- Это позволяет тестировать type-dependent ветки без реального Discord API.

## PDIS-T003 — Автоматические AsyncMock для coroutine-методов
- Mock-инфраструктура сама определяет async API и создаёт `AsyncMock` вместо обычного mock.
- Дополнительные методы можно вручную добавить в async allowlist.

## PDIS-T004 — Mock event loop без реального scheduling
- `create_task()` в тестах не запускает фоновые задачи, а закрывает переданную coroutine.
- Это предотвращает `coroutine was never awaited` warnings и делает тесты детерминированными.

## PDIS-T005 — Fake Redis на каждый тест
- Redis-dependent тесты получают отдельную fakeredis session в `asyncSetUp`.
- Перед каждым тестом база полностью очищается, после теста соединение закрывается.

## PDIS-T006 — Общий CommandTestCase для permission assertions
- Базовый тестовый класс содержит reusable assertion, проверяющий Discord permissions и точный набор недостающих разрешений.

## PDIS-T007 — assertNotLogs как отрицательная проверка
- Можно явно тестировать, что операция **не** генерирует логов выше заданного уровня.
- При нарушении assertion выводит количество и содержимое записей, сохраняя исходные handlers/level/propagate.

## PDIS-T008 — Multi-patch autospec decorator
- Один decorator патчит несколько атрибутов target через `autospec=True` и `spec_set=True`.
- Можно выбрать, передавать ли созданные mocks в тестируемую функцию.

## PDIS-T009 — Subtests для матриц входов
- Набор input/output кейсов запускается как независимые subtests с именованными параметрами.
- Один плохой вариант не скрывает результаты остальных и прямо показывает проблемный input.

## PDIS-T010 — Тесты структуры команд по всему приложению
- Автотест проходит все extensions/cogs и рекурсивно собирает root/subcommands.
- Проверяется глобальная уникальность qualified names и aliases, предотвращая случайное shadowing команд.

## PDIS-T011 — Проверка всех cog extensions на загрузку
- Общий тест может импортировать все модули `exts`, найти определённые в них Cogs и проверить setup/load behavior.
- Новый cog автоматически попадает в инфраструктурную проверку без отдельного ручного списка.

## PDIS-T012 — Проверка listener registration как контракта
- Тесты могут проверять наличие Discord listener metadata у методов, а не только результат их вызова.
- Это ловит ситуацию, когда обработчик существует, но больше не зарегистрирован как listener.

## PDIS-T013 — Реалистичные Discord fixtures через настоящие модели
- Для сложных mocks сначала создаётся реальный `discord.Guild`/`Role`/`Message` из минимального data payload, затем он используется как `spec`.
- Такой подход автоматически синхронизирует mock с фактическим API объекта.

## PDIS-T014 — Тестируемые API diff-модели
- Синхронизация внешней БД и Discord проверяется через отдельные `created/updated/deleted` diff-наборы.
- Один fixture может покрывать комбинации добавления, изменения и удаления без реального API.

## PDIS-T015 — Тестирование частичных API ошибок по статусу
- Ожидаемые HTTP errors (например, 404 для уже исчезнувшего объекта) проверяются отдельно от неожиданных 500.
- Система явно гарантирует: ожидаемая ошибка игнорируется, неизвестная пробрасывается.

## PDIS-T016 — Event-фильтрация по guild перед API mutation
- Тесты фиксируют, что gateway events из чужих guild не приводят к изменениям во внешней БД.
- Такой контракт стоит защищать отдельными тестами для каждого mutation listener.

## PDIS-T017 — Async test isolation через `IsolatedAsyncioTestCase`
- Каждый async тест получает изолированный event loop lifecycle.
- Это снижает утечки состояния между асинхронными тестами.

## PDIS-T018 — Проверка конфигурационных моделей через временный `.env`
- Конфигурационные классы тестируются на реальном env-файле и одновременно на runtime environment variables.
- Можно проверять приоритет env над default значениями и вложенные Pydantic models.

## PDIS-T019 — Coverage как измерение веток, а не гарантия корректности
- Branch coverage используется как минимальный индикатор, но дополнительно нужны realistic-input tests для веток, которые coverage формально уже посещает.

## PDIS-T020 — Отдельный manual/integration слой поверх unit tests
- Даже 100% unit/branch coverage не считается доказательством работы Discord API.
- Для внешних интеграций сохраняется отдельный integration/manual validation слой.

## PDIS-T021 — Last-failed test rerun
- После массового запуска можно повторно запускать только тесты, упавшие в предыдущем прогоне (`--lf`), ускоряя локальный цикл исправления.

## PDIS-T022 — Failed-first test ordering
- Следующий тестовый прогон сначала запускает недавно падавшие тесты (`--ff`), чтобы быстрее проверить исправление.

## PDIS-T023 — Параллельный test runner
- Независимые тесты запускаются параллельно по worker-процессам (`-n auto`), сокращая время CI.
- Это требует строгой изоляции состояния и поэтому усиливает ценность PDIS-T005.

## PDIS-T024 — Быстрый targeted test command
- Разработчик может запускать один конкретный test file вместо всего suite, сохраняя тот же окружение/runner.

## PDIS-T025 — Отдельный coverage report после тестового прогона
- Coverage собирается отдельно от запуска тестов и может генерировать HTML/terminal отчёт.
- В отчёт можно включать непокрытые lines и branches для направленной работы.
