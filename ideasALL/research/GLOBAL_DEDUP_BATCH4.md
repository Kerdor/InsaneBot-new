# GLOBAL DEDUP — BATCH 4

Тематические области: Moderation / Tickets.

Правило: исходные IDs сохраняются; одинаковые механики объединяются, а уникальные ограничения, UX и архитектурные варианты сохраняются внутри канона.

## Moderation

### GD-116 — Иерархическая проверка модерации
Источники: MOD-001, MOD-045–048.
Канон: перед moderation action проверяются роль вызывающего и роль бота относительно цели; owner получает bypass; ошибки объясняют конфликт.

### GD-117 — Защита self/bot targeting
Источники: MOD-049–050, MOD-076.
Канон: destructive moderation не применяется к самому модератору или боту; правило действует и для массовых операций.

### GD-118 — Проверка наличия Member/User перед действием
Источники: MOD-051–055, MOD-060.
Канон: Member-only actions требуют участника текущего сервера; действия по User могут работать для отсутствующих участников при повышенных правах; входные ID нормализуются и валидируются.

### GD-119 — Проверка фактической Discord-модерируемости
Источники: MOD-068–069, MOD-078.
Канон: после общей иерархии дополнительно проверяются `moderatable`/`kickable` и реальные ограничения Discord.

### GD-120 — Warning system
Источники: MOD-002–003, MOD-021, MOD-023–027, MOD-060–065.
Канон: предупреждения с историей, удалением отдельных/all warnings, причинами, points, ID/порядковым номером и настройками DM/self-view.

### GD-121 — Warning points automation
Источники: MOD-021–022.
Уникальный слой: накопленные warning points могут запускать действия по именованным пороговым правилам; при снижении points возможна обратная реакция.

### GD-122 — Настраиваемый warn workflow
Источники: MOD-023–027.
Канон: именованные причины с points, optional custom reasons, отдельный warn channel, DM toggle и настройка показа модератора.

### GD-123 — История имён пользователя
Источник: MOD-028.
Канон: хранение предыдущих username/display name/server nickname и просмотр истории; ограничение последними значениями сохраняется.

### GD-124 — Безопасный rename
Источник: MOD-029.
Канон: снятие nickname пустым аргументом, проверка длины и полной иерархии Discord.

### GD-125 — Anti-repeat message protection
Источник: MOD-030.
Канон: короткая история повторов пользователя и автоматическое удаление после настраиваемого порога.

### GD-126 — Mention spam detection modes
Источник: MOD-031.
Уникальная настройка: считать все упоминания либо только уникальные сущности.

### GD-127 — Reinvite после unban
Источник: MOD-032.
Канон: после unban можно автоматически создать/использовать invite с fallback-цепочкой vanity → permanent → temporary.

### GD-128 — Обязательная причина moderation action
Источник: MOD-033.
Канон: серверная настройка может требовать reason для moderation actions.

### GD-129 — Ban message deletion policy
Источник: MOD-034.
Канон: на сервере задаётся число дней сообщений для удаления при ban, в пределах Discord-лимита.

### GD-130 — Default tempban duration
Источник: MOD-035.
Канон: серверная длительность по умолчанию для tempban + фоновое снятие после истечения.

### GD-131 — Ban DM customization
Источник: MOD-036.
Канон: к DM о ban можно добавить настраиваемый текст, например инструкции/апелляцию.

### GD-132 — Mute implementation modes
Источник: MOD-037.
Канон: mute может использовать отдельную mute-role либо permission overwrites; режим выбирается конфигурацией.

### GD-133 — Channel-scoped mute
Источник: MOD-038.
Уникальная механика: mute действует только в конкретном канале, состояния разных каналов независимы.

### GD-134 — Timed mute/unmute
Источники: MOD-039–043.
Канон: server/channel mute имеют срок окончания, фоновой обработчик снимает ограничения; ошибки уходят в notification channel; DM уведомления настраиваются; Administrator защищён.

### GD-135 — Moderation service layer
Источник: MOD-044.
Канон: ban/kick/timeout/unban реализуются через общий сервис, а команды остаются orchestration-слоем.

### GD-136 — Moderation case records
Источники: COMM-009, MOD-056–058.
Канон: каждое moderation action может создавать case с ID, target, executor, reason и action-specific metadata; результат связан с audit/log pipeline.

### GD-137 — Safe default reasons
Источник: MOD-059.
Канон: действия без обязательной причины используют безопасный default reason; warn остаётся отдельным случаем с обязательной причиной.

### GD-138 — Timeout presets
Источники: MOD-066–067.
Канон: timeout предлагает фиксированные человекочитаемые длительности и отображает выбранный период обратно пользователю.

### GD-139 — UnTimeout validation
Источники: MOD-070–071.
Канон: снятие timeout проверяет наличие активного timeout и использует отдельную audit reason.

### GD-140 — Mass moderation with partial results
Источники: MOD-072–080.
Канон: mass ban/kick обрабатывает цели независимо, возвращает success/skipped/failed, пропускает недопустимые цели и продолжает работу после ошибки одной цели.

### GD-141 — Mass moderation input normalization
Источники: MOD-073–077.
Канон: массовый ввод поддерживает пробелы/запятые/mentions, валидирует IDs, ограничивает размер операции и защищает self/bot.

### GD-142 — Per-command destructive-action rate limits
Источники: MOD-080–082.
Канон: destructive commands имеют отдельные abuse limits; лимит зависит от конкретной команды.

### GD-143 — Safe purge
Источники: MOD-015–020, MOD-081, MOD-083–086.
Канон: cleanup по различным условиям, bulk limit 1–100, защита старых сообщений, подтверждение опасных массовых операций, понятный результат и auto-delete служебного ответа.

### GD-144 — Bot-message cleanup
Источники: MOD-016–017.
Канон: отдельная очистка сообщений самого бота, включая команды/aliases/custom commands, с текстовым фильтром и fallback на одиночное удаление.

### GD-145 — Duplicate message cleanup
Источник: MOD-018.
Канон: поиск повторов среди последних сообщений с сохранением первой копии и сравнением релевантных полей сообщения.

### GD-146 — Channel lock/unlock
Источники: MOD-087–091.
Канон: lock/unlock через permission overwrite @everyone с проверкой текущего состояния и audit reason; контекст канала сохраняется для аудита.

### GD-147 — Staff DM
Источники: MOD-092–098.
Канон: служебная DM-команда для staff с anonymous mode, permission check, bot-target protection, sanitization, length limit и обработкой закрытых DM.

### GD-148 — Moderation send-message utility
Источник: MOD-099–100.
Канон: staff может отправлять сообщение в выбранный поддерживаемый текстовый канал или текущий канал с валидацией типа канала.

## Tickets

### GD-149 — Ticket panel
Источник: TICKET-001.
Канон: интерактивная панель создания тикета с настраиваемым текстом и компонентом открытия.

### GD-150 — One active ticket per user
Источник: TICKET-002.
Канон: пользователь не может открыть второй тикет, пока предыдущий активен.

### GD-151 — Ticket claim/unclaim
Источники: TICKET-003, COMM-010, MOD-006.
Канон: staff может взять тикет в работу и снять назначение.

### GD-152 — Ticket priority
Источники: TICKET-004, COMM-011.
Канон: приоритет тикета можно повышать/понижать для staff workflow.

### GD-153 — Ticket close states
Источники: TICKET-005–007.
Канон: обычное закрытие является состоянием workflow; instant close и instant delete сохраняются как быстрые альтернативные пути.

### GD-154 — Ticket rename
Источник: TICKET-008.
Канон: переименование уже созданного тикета.

### GD-155 — Ticket participants management
Источник: TICKET-009.
Канон: добавление/удаление участников существующего тикета без создания нового обращения.

### GD-156 — Ticket follow-up notification
Источник: TICKET-010.
Канон: staff может уведомить автора тикета о необходимости ответа; вариант с автоматическим закрытием после периода сохраняется.

### GD-157 — Ticket transcript
Источники: TICKET-011, COMM-013.
Канон: сохранение истории закрытого тикета; HTML transcript остаётся допустимым форматом реализации.

### GD-158 — Custom ticket message
Источник: TICKET-012.
Канон: UI сообщения открытого тикета настраивается отдельно от workflow.

### GD-159 — Ticket limits
Источники: TICKET-013, COMM-012.
Канон: лимит количества активных тикетов; отдельно сохраняется более строгая модель one-active-per-user из GD-150.

### GD-160 — Multiple ticket systems
Источники: TICKET-014, MOD-009.
Канон: сервер может иметь несколько независимых ticket setup/configurations; число систем является конфигурационным ограничением.

## Cross-theme notes

- MOD-021/022 warning points остаются частью moderation domain и не объединяются с Economy currency.
- MOD-056–058 и COMM-009 объединены в общий moderation case concept; ticket transcript остаётся отдельной историей обращения.
- COMM-010/011/012/013 уже покрыты GD-151/152/159/157, поэтому отдельные community entries не создаются повторно.
- TICKET-005 и TICKET-006 не схлопываются полностью: обычный close меняет состояние workflow, instantclose — отдельный быстрый путь.
