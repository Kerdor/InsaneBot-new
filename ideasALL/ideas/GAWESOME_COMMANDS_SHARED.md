# GAwesomeBot — Shared Commands

Источник: `GAwesomeBot/bot`
Ветка: `indev-4.0.2`
Каталог: `Commands/Shared/`

## Общая модель

- **GAB-SH-001** — Shared-команда с минимальным контрактом: получает только главный объект приложения, сообщение и metadata команды.
- **GAB-SH-002** — Общий контракт Shared-команд отдельно документируется от полноценных команд.
- **GAB-SH-003** — `commandData` используется как metadata текущей команды, а дополнительные данные Shared-команда может получать только при необходимости.
- **GAB-SH-004** — Shared namespace позволяет создавать служебные команды, работающие поверх нескольких контекстов.
- **GAB-SH-005** — Shared-команды могут использовать глобальные настройки/объекты приложения без дублирования их получения.

## Debug / диагностика

- **GAB-SH-006** — `debug` без аргументов показывает компактный общий диагностический статус.
- **GAB-SH-007** — `debug -h` / `--help` показывает отдельный каталог диагностических аргументов.
- **GAB-SH-008** — Help для debug явно указывает, что `--help` имеет приоритет над остальными аргументами.
- **GAB-SH-009** — Debug поддерживает независимые диагностические секции, которые можно запрашивать выборочно.
- **GAB-SH-010** — Флаг `--no-general` скрывает стандартную диагностику и оставляет только явно запрошенные секции.
- **GAB-SH-011** — Диагностика процесса показывает runtime, версию Node, путь к executable, PID и текущую рабочую директорию.
- **GAB-SH-012** — Диагностика процесса показывает ID текущего shard.
- **GAB-SH-013** — Диагностика процесса показывает выделенный heap и RSS.
- **GAB-SH-014** — Диагностика процесса показывает uptime.
- **GAB-SH-015** — Диагностика Discord-клиента показывает bot tag и ID.
- **GAB-SH-016** — Диагностика Discord-клиента показывает текущую latency/ping.
- **GAB-SH-017** — Диагностика Discord-клиента показывает uptime клиента отдельно от process uptime.
- **GAB-SH-018** — Диагностика master-процесса запрашивается через IPC, а не через локальное состояние shard.
- **GAB-SH-019** — Master diagnostics показывают PID master-процесса.
- **GAB-SH-020** — Master diagnostics показывают RSS master-процесса.
- **GAB-SH-021** — Master diagnostics показывают количество зарегистрированных пользователей и guilds.
- **GAB-SH-022** — Для диагностического запроса к БД показывается длительность запроса.
- **GAB-SH-023** — OS diagnostics показывают нормализованное имя ОС вместо сырого platform-кода.
- **GAB-SH-024** — Неизвестная ОС не ломает диагностику: показывается исходный platform identifier.
- **GAB-SH-025** — OS diagnostics показывают количество CPU cores и архитектуру.
- **GAB-SH-026** — OS diagnostics показывают общий и используемый объём RAM.
- **GAB-SH-027** — OS diagnostics показывают имя системного пользователя.
- **GAB-SH-028** — Debug умеет показывать текущие права пользователя внутри самого бота.
- **GAB-SH-029** — Права maintainer разделяются на обычного maintainer, sudo-maintainer и host.
- **GAB-SH-030** — Host получает отдельное явное описание неограниченных полномочий.
- **GAB-SH-031** — Пользователю без maintainer-прав явно сообщается, что он не maintainer.
- **GAB-SH-032** — Список доступных maintainer permissions фильтруется по уровню самого пользователя.
- **GAB-SH-033** — Версионная диагностика получает metadata версии из центрального API.
- **GAB-SH-034** — При недоступности version API debug продолжает работу с fallback `valid=false`.
- **GAB-SH-035** — При неизвестной версии показываются локальные branch/version identifiers вместо падения.
- **GAB-SH-036** — При валидной версии показываются имя версии, branch, commit SHA и tag.
- **GAB-SH-037** — Ошибка внешнего version API выводится отдельной диагностической секцией.
- **GAB-SH-038** — Debug формирует несколько диагностических полей в одном embed вместо отправки отдельного сообщения на каждую секцию.
- **GAB-SH-039** — Общая диагностика показывает shard ID, общее число shards, RAM процесса, PID, uptime, число guilds и ping.
- **GAB-SH-040** — Footer debug подсказывает пользователю, где посмотреть дополнительные аргументы.
- **GAB-SH-041** — Короткие флаги имеют длинные aliases (`-p`/`--process`, `-v`/`--version`, и т. п.).
- **GAB-SH-042** — Один debug-запрос может комбинировать несколько диагностических флагов.

## Eval / developer tooling

- **GAB-SH-043** — Developer eval-команда поддерживает выполнение async-кода через обёртку async function.
- **GAB-SH-044** — Eval определяет специальный unsafe-режим отдельным `--unsafe` флагом.
- **GAB-SH-045** — Без unsafe eval автоматически удаляет/нейтрализует обращения к чувствительным токенам и секретным полям.
- **GAB-SH-046** — Список потенциально чувствительных значений дополнительно используется для маскирования результата после выполнения.
- **GAB-SH-047** — Результат eval проходит через regex-based censoring перед отправкой пользователю.
- **GAB-SH-048** — Секреты в результате заменяются специальным безопасным placeholder вместо раскрытия исходного значения.
- **GAB-SH-049** — Eval принимает JavaScript code block вида ` ```js ... ``` ` и снимает внешнее форматирование перед исполнением.
- **GAB-SH-050** — Eval поддерживает как выражения, возвращающие значение, так и код с явным `return`.
- **GAB-SH-051** — Нескаляные результаты форматируются через structured inspection, а не через обычное преобразование в строку.
- **GAB-SH-052** — Глубина inspect ограничивается, чтобы большие/глубокие объекты не разрастались бесконтрольно.
- **GAB-SH-053** — Время выполнения eval измеряется отдельно и показывается в результате.
- **GAB-SH-054** — Ошибка выполнения eval возвращается пользователю как отдельный error result с stack trace.
- **GAB-SH-055** — При отсутствии кода eval не пытается выполнить пустой ввод, а показывает понятный prompt.
- **GAB-SH-056** — Большой результат eval автоматически выносится во внешний gist вместо обрезания сообщения.
- **GAB-SH-057** — Для внешнего eval-результата используется отдельный файл с понятным именем (`eval_results.js`).
- **GAB-SH-058** — Результат gist отправляется только после успешной загрузки и наличия URL.
- **GAB-SH-059** — Ошибки eval не ломают саму команду и возвращаются через пользовательский error embed.
- **GAB-SH-060** — Developer tooling различает обычный безопасный режим и явно выбранный unsafe-режим.

## Reload / hot-reload

- **GAB-SH-061** — Reload принимает команды с явным namespace: `pm.<command>`, `public.<command>`, `shared.<command>`.
- **GAB-SH-062** — Reload умеет работать не только с командами, но и с events.
- **GAB-SH-063** — Reload поддерживает отдельные типы `events`, `routes`, `modules` как расширяемые namespace.
- **GAB-SH-064** — Reload без аргументов показывает примеры синтаксиса для каждого поддерживаемого типа.
- **GAB-SH-065** — Reload без аргументов отдельно сообщает, что несколько целей можно передавать через пробел.
- **GAB-SH-066** — Одна команда reload может перезагрузить несколько независимых целей за один вызов.
- **GAB-SH-067** — Для событий поддерживается wildcard `events.*` для полной перезагрузки.
- **GAB-SH-068** — Для PM/Public/Shared поддерживается wildcard `*` для полной перезагрузки namespace.
- **GAB-SH-069** — Для каждого namespace используется собственный reload handler.
- **GAB-SH-070** — Перед reload Public/Shared проверяется существование command metadata в общем реестре команд.
- **GAB-SH-071** — Public и Shared command names нормализуются через отдельный resolver перед reload.
- **GAB-SH-072** — Неизвестная команда получает отдельную диагностическую ошибку с указанием namespace.
- **GAB-SH-073** — Неизвестный тип reload получает отдельную ошибку вместо молчаливого fallback.
- **GAB-SH-074** — Неизвестный event различается от обычной ошибки во время его reload.
- **GAB-SH-075** — Ошибка reload содержит stack trace для developer diagnosis.
- **GAB-SH-076** — Успешный reload возвращает явное подтверждение конкретной цели.
- **GAB-SH-077** — Успешный wildcard reload возвращает отдельное сообщение о полной перезагрузке namespace.
- **GAB-SH-078** — Reload логирует actor ID и целевой command/event.
- **GAB-SH-079** — Ошибки reload также логируются с actor ID и целевой сущностью.
- **GAB-SH-080** — Reload различает `soft error` для неверного ввода и полноценную ошибку исполнения.
- **GAB-SH-081** — Ошибка отсутствующего metadata-файла объясняет, что данные команды не найдены в command registry.
- **GAB-SH-082** — После reload команда продолжает использовать общий registry вместо создания нового отдельного пути разрешения.
- **GAB-SH-083** — Developer reload использует единый синтаксис `type.command` для разных классов runtime-объектов.
- **GAB-SH-084** — Тип по умолчанию для параметра без namespace — `public`.
- **GAB-SH-085** — Валидация namespace выполняется до попытки реального reload.
- **GAB-SH-086** — Несколько reload-операций из одного сообщения обрабатываются независимо, поэтому ошибка одной цели не обязана отменять остальные.
- **GAB-SH-087** — Результат каждой операции reload имеет собственный success/error response.

## Дополнительные общие идеи

- **GAB-SH-088** — Shared-команды подходят для developer/admin tooling, которое должно быть доступно в нескольких command contexts.
- **GAB-SH-089** — Служебные команды могут отдавать структурированные диагностические данные без создания отдельных команд под каждый параметр.
- **GAB-SH-090** — Для developer-команд полезно разделять пользовательский ответ, внутренний лог и технический stack trace.
- **GAB-SH-091** — Длинные технические результаты следует автоматически переводить из Discord message в внешний артефакт.
- **GAB-SH-092** — Diagnostic command может использовать модульный набор независимых sections вместо монолитного ответа.
- **GAB-SH-093** — Служебные команды должны иметь явные help-ветки с полным списком доступных режимов.
- **GAB-SH-094** — Developer-команды должны иметь безопасный default и явно обозначенный режим, расширяющий полномочия.
