# GAwesomeBot — Commands/Private

Источник: `GAwesomeBot/bot`, ветка `indev-4.0.2`

Каталог `Commands/Private/` обработан полностью: `giveaway.js`, `index.js`, `poll.js`, `say.js`.

## GAB-PR-001 — Единый приватный relay-слой
`Commands/Private/index.js` экспортирует приватные серверные операции как отдельные исполнители (`poll`, `giveaway`, `say`). Это позволяет DM-командам выбирать серверную операцию через единый внутренний namespace.

## GAB-PR-002 — Повторяемый алгоритм поиска сервера для DM-команды
Приватные исполнители ищут сервер последовательно: точное имя/регистронезависимое имя → ID → персональный server alias пользователя. Результат дополнительно валидируется фактом членства пользователя на сервере.

## GAB-PR-003 — Membership gate на этапе server resolution
Даже если найден сервер по имени или ID, он считается подходящим только если пользователь действительно состоит на нём. Это не просто lookup, а lookup + authorization precondition.

## GAB-PR-004 — Приватный relay учитывает server blocklist
Перед выполнением удалённой операции проверяется серверный список заблокированных пользователей. Заблокированный пользователь получает фактический early-return без выполнения действия.

## GAB-PR-005 — Channel resolution отдельным этапом
После выбора сервера приватная команда отдельно разрешает текстовый канал через общий `channelSearch`, а не пытается напрямую использовать введённое имя как ID.

## GAB-PR-006 — Разделение channel-not-found и invalid-channel-type
Ошибку поиска канала и ситуацию, когда канал найден, но не является текстовым, можно показывать по-разному. Это полезный UX-паттерн для удалённых команд.

## GAB-PR-007 — Lazy creation channel state
Если документ канала отсутствует в серверном документе, приватная команда добавляет канал в persistent state перед обращением к его настройкам/состоянию.

## GAB-PR-008 — Remote `say` с авторской атрибуцией
Сообщение, отправляемое через DM-relay, публикуется как embed с именем и аватаром инициатора. Получатели видят, кто фактически запросил публикацию.

## GAB-PR-009 — Remote `say` проверяет VIEW_CHANNEL + SEND_MESSAGES пользователя
Даже при наличии требуемого уровня доступа бота пользователь не может использовать relay для канала, который сам не может видеть или куда не может писать. Это отдельная проверка пользовательского доступа к target channel.

## GAB-PR-010 — Удаление исходного DM-промпта при невозможности выполнить remote say
В отдельных ошибочных ветках инициирующее DM-сообщение удаляется, после чего пользователю отправляется отдельное объяснение. Это вариант очистки временного command UI.

## GAB-PR-011 — Удалённый say запрашивает содержимое отдельным DM-шагом
Сервер и канал могут быть определены одной командой, а сам текст для публикации запрашивается отдельным приватным сообщением с timeout до 5 минут.

## GAB-PR-012 — Remote `say` подтверждает результат ссылкой на target channel по имени
После успешной отправки relay сообщает пользователю, где искать опубликованное сообщение, вместо повторения всего содержимого.

## GAB-PR-013 — Poll: повторный вызов автором превращается в end-flow
Если автор уже имеет активный poll в выбранном канале, новый запуск не создаёт второй poll: приватный flow спрашивает, хочет ли автор завершить существующий и показать результаты.

## GAB-PR-014 — Poll: повторный голос пользователя превращается в revoke-flow
Если пользователь уже голосовал, relay предлагает удалить существующий голос. Это отдельный UX-flow вместо безусловного отказа или перезаписи.

## GAB-PR-015 — Poll revoke удаляет конкретную запись пользователя
Отмена голоса адресно удаляет запись response по user ID, а не сбрасывает весь poll или список ответов.

## GAB-PR-016 — После revoke пользователь получает явную инструкцию проголосовать заново
Подтверждение удаления голоса одновременно объясняет, как повторно открыть poll. Это превращает ошибочное/изменившееся решение пользователя в полноценный re-vote flow.

## GAB-PR-017 — Poll voting в DM остаётся анонимным для сервера
Пользователь выбирает вариант через DM, а в публичный канал не отправляет свой выбор напрямую. В state сохраняется связь user → vote, но UI голосования проходит приватно.

## GAB-PR-018 — Большой список poll options разбивается на страницы
Варианты голосования группируются блоками по 10 и показываются через paginated embed. Это позволяет не ломать UX при большом числе вариантов.

## GAB-PR-019 — Нумерация вариантов стабильна между страницами
Каждый option получает глобальный номер, а не номер внутри текущей страницы. Пользователь выбирает по этому номеру независимо от pagination.

## GAB-PR-020 — Poll menu предупреждает о поведении pagination reaction
DM-интерфейс явно предупреждает пользователя, что для смены страницы может понадобиться снять и заново поставить реакцию. Техническое ограничение UI превращено в пользовательскую подсказку.

## GAB-PR-021 — Poll input фильтруется callback-валидатором
Ожидаемое DM-сообщение принимается только если после trim это число, оно больше нуля и не превышает число вариантов. Некорректные сообщения не считаются валидным ответом flow.

## GAB-PR-022 — Отдельный короткий timeout для poll owner confirmation
Подтверждение завершения активного poll ждёт ответ около 1 минуты, тогда как само голосование получает 4 минуты. Разные шаги flow имеют разные SLA.

## GAB-PR-023 — Poll creation имеет разные timeout по шагам
Название/вопрос ожидается около 1 минуты, список вариантов — до 5 минут. Длинный ввод получает больше времени, чем короткий confirmation.

## GAB-PR-024 — Poll default options через `.`
При создании poll точка является shorthand для стандартных `No/Yes` вариантов. Это сокращает наиболее частый двухвариантный сценарий.

## GAB-PR-025 — Poll options вводятся одной строкой через comma-separated syntax
Вместо отдельного prompt для каждого варианта пользователь вводит все варианты одной строкой, после чего строка нормализуется в массив.

## GAB-PR-026 — После создания poll DM показывает все его варианты
Создателю показывается итоговый список вариантов через тот же pagination-механизм, который используется для голосования.

## GAB-PR-027 — Giveaway: существующий giveaway имеет три режима по состоянию пользователя
Для активного giveaway relay различает владельца, уже участвующего пользователя и нового пользователя. Для каждого состояния используется отдельный confirmation/action flow.

## GAB-PR-028 — Giveaway owner может завершить свой активный giveaway через DM
Повторный DM-запуск для владельца не создаёт новый giveaway: бот предлагает немедленно закончить существующий и выбрать победителя.

## GAB-PR-029 — Giveaway participant может выйти через DM
Уже записанному участнику предлагается удалить собственное участие. Это self-service управление entry без необходимости идти в исходный канал.

## GAB-PR-030 — Giveaway participant получает отдельное подтверждение после leave
После удаления entry пользователь получает явный success response; отказ оставить участие также имеет отдельный позитивный ответ.

## GAB-PR-031 — Giveaway join выполняется через yes/no confirmation
Новый пользователь не добавляется автоматически: DM сначала спрашивает согласие и принимает только ответы, распознаваемые как affirmative.

## GAB-PR-032 — Giveaway join/leave/end используют общий affirmative dictionary
Проверка согласия основана на централизованном наборе `yesStrings`, а не на одном жёстко заданном слове `yes`. Это позволяет локализовать/расширять affirmative vocabulary в одном месте.

## GAB-PR-033 — Giveaway creation: secret prize вводится до публичного title
Первым шагом создатель передаёт значение приза, причём UI явно сообщает, что увидеть его сможет только победитель. Затем отдельно задаются title и duration.

## GAB-PR-034 — Secret giveaway payload отделён от display title
В модели создания prize/secret и название giveaway передаются отдельными значениями. Это позволяет публично показывать понятное название, не раскрывая сам секрет.

## GAB-PR-035 — Giveaway duration поддерживает natural-duration parser
Пользователь может вводить длительность в человекочитаемом формате, а не только в миллисекундах/числах.

## GAB-PR-036 — Giveaway duration shorthand `.` = 1 hour
Точка используется как быстрый выбор стандартной длительности 1 час.

## GAB-PR-037 — Некорректная giveaway duration безопасно заменяется default
При `NaN` или неположительной длительности flow не падает и не просит заново проходить весь wizard: пользователь получает предупреждение, после чего используется 1 час.

## GAB-PR-038 — Giveaway creation permission проверяется после resolution target
Сначала определяется конкретный сервер/канал и состояние giveaway, затем проверяется требуемый bot-admin level или maintainer bypass. Это предотвращает создание в неподходящем target.

## GAB-PR-039 — Maintainer bypass для приватных административных relay-команд
Внутренние приватные исполнители допускают отдельный список глобальных maintainers как обход обычного server command admin-level.

## GAB-PR-040 — Poll и giveaway имеют разные сравнения admin threshold
В исходнике poll использует `>=` для допустимого уровня, giveaway — `>` в соответствующей ветке. Это пример того, что command-specific authorization может иметь собственные boundary semantics и их нельзя автоматически унифицировать без проверки.

## GAB-PR-041 — Remote command failures редактируют уже существующий DM UI
Вместо отправки длинной цепочки новых сообщений некоторые ошибки заменяют содержимое исходного progress/prompt message. Это уменьшает DM-spam.

## GAB-PR-042 — Private relay сохраняет correlation с исходным DM message
`initMsg`/`initMsgID` используется для поиска и редактирования исходного пользовательского сообщения. Такой ID можно использовать как correlation ID для длинного asynchronous flow.

## GAB-PR-043 — Awaited DM flow имеет явный timeout и silent timeout exit
Если пользователь не отвечает в установленный срок, исполнитель завершает flow без выполнения действия. Timeout является нормальной веткой состояния, а не exception для пользователя.

## GAB-PR-044 — Удалённая операция сначала материализует актуальный server document
Poll/say используют `populateDocument`/получение server document перед изменением channel state. Это отделяет Discord entity lookup от persistent configuration/state.

## GAB-PR-045 — Poll использует clone query для адресного изменения вложенного channel state
Вложенные poll responses изменяются через cloned query с ID конкретного channel document. Это даёт паттерн точечного обновления вложенного state вместо ручной реконструкции всего документа.

## GAB-PR-046 — Giveaway использует push/pull для participant membership
Добавление участника и удаление участника реализованы как адресные операции над массивом IDs. Это естественная модель для toggle-like membership state.

## GAB-PR-047 — Private command error response содержит support escalation
Необработанная ошибка пользователю сопровождается stack/error information и рекомендацией обратиться к server admin. Это отдельный fallback UX для внутренних command flows.

## GAB-PR-048 — Private command layer повторно использует общие Discord search/permission primitives
Вместо собственного lookup-кода приватные команды используют общие server/channel search и permission helpers. Это снижает расхождение поведения между публичными и DM-командами.

## GAB-PR-049 — Private namespace минимален и предметен
Внутренний слой содержит ровно три server-side relay operations: poll, giveaway и say. Остальная PM-логика остаётся в PM namespace, а Private выступает узким execution layer.
