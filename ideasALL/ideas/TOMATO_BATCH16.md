# Tomato6966 — Batch 16

Источник: `Tomato6966/Multipurpose-discord-bot`
Ветка: `new_2025`
Область: оставшиеся root-level handlers и повторная сверка крупных функциональных handlers.

## TOM-231 — DM-уведомления Giveaway о состоянии участия
- При успешном входе в giveaway участнику отправляется подтверждение в DM с призом, количеством победителей и его bonus entries.
- При выходе из giveaway участнику отправляется отдельное DM-уведомление.
- При недопустимом участнике бот объясняет причину в DM и автоматически удаляет его реакцию.
- При победе и reroll победитель получает отдельное DM-уведомление с призом и ссылкой на giveaway.
- Это отдельный notification layer поверх обычной giveaway-механики.

## TOM-232 — Автоматическая передача владельца временной Voice-комнаты
- Если владелец созданной Join-to-Create комнаты покидает её, система автоматически выбирает одного из оставшихся участников новым владельцем.
- Новому владельцу выдаются права управления комнатой, а права старого владельца удаляются.
- Новый владелец получает DM с уведомлением о передаче ownership и доступных voice-командах.
- Работает как fallback для сохранения управляемости временной комнаты без ручной передачи.

## TOM-233 — Периодическая проверка и очистка Join-to-Create комнат
- JTC handler регулярно проверяет trigger channels и уже созданные временные комнаты.
- Проверки выполняются также сразу после `ready`, чтобы восстановить/очистить состояние после перезапуска бота.
- Пустые временные комнаты удаляются вместе с runtime-записями mapping/owner.
- Это self-healing/cleanup слой поверх обычного voiceStateUpdate создания комнат.

## TOM-234 — Двухшаговое подтверждение закрытия/удаления Ticket
- Действие закрытия или удаления тикета не выполняется мгновенно: сначала публикуется подтверждающий компонент `Verify this Step`.
- Подтверждение действует ограниченное время через component collector.
- Если нужный пользователь не подтвердил действие вовремя, сообщение становится неактивным и помечается как failed.
- После подтверждения закрытый тикет получает новое состояние и дальнейшие действия выполняются только после проверки прав.

## TOM-235 — Закрытие Ticket с отзывом доступа пользователя и переносом
- При закрытии тикета пользователь удаляется из списка участников ticket и получает deny на `VIEW_CHANNEL`/`SEND_MESSAGES`.
- Канал может быть перемещён в отдельную closed-ticket category при наличии места.
- Имя канала изменяется с `ticket` на `closed`.
- Состояние ticket сохраняется как `closed`, поэтому система может отличать закрытый канал от активного.

## TOM-236 — CAPTCHA Quarantine Role с автоматической настройкой прав
- При включённой Welcome CAPTCHA бот ищет специальную CAPTCHA-role и при отсутствии создаёт её автоматически.
- Для этой роли на серверных каналах выставляется запрет `VIEW_CHANNEL`, `SEND_MESSAGES`, `ADD_REACTIONS`, `CONNECT` и `SPEAK`.
- Новый участник получает CAPTCHA-role до прохождения проверки.
- Таким образом CAPTCHA реализуется как полноценный quarantine layer, а не только как сообщение с кодом.

## TOM-237 — Защита Leveling от повторяющихся сообщений
- Перед начислением XP сохраняется нормализованное содержимое предыдущего сообщения пользователя.
- Если новое сообщение совпадает с предыдущим после удаления пробелов и приведения к нижнему регистру, XP повторно не начисляется.
- Это отдельная анти-фарм защита внутри ranking/leveling handler.

## TOM-238 — Автоматические Role Rewards за уровень
- При достижении нового уровня система проверяет guild-scoped mapping `level -> role`.
- Если для уровня настроена роль, она автоматически выдаётся пользователю.
- Role reward выполняется непосредственно в момент level-up и не требует отдельной команды.

## TOM-239 — Переключение голоса Suggestion с возможностью смены решения
- Пользователь может изменить свой голос: при upvote предыдущий downvote снимается и наоборот.
- Повторный одинаковый голос блокируется.
- Система хранит отдельные списки проголосовавших пользователей для обоих вариантов.
- Через кнопку `Who voted?` можно открыть ephemeral-список проголосовавших; при большом числе показывается ограниченная выборка и количество остальных.

## TOM-240 — Декларативный Slash Command Builder из файлов команд
- Slash-команды автоматически собираются из файловой структуры `slashCommands/`.
- Папки превращаются в slash-command groups, а файлы внутри — в subcommands.
- Типы параметров (`User`, `Integer`, `String`, `Channel`, `Role`) и варианты выбора (`StringChoices`, `IntChoices`) описываются в данных самой команды.
- Генерируется единый массив JSON-команд для последующей регистрации, а runtime-команды хранятся в общей коллекции.
- Это архитектурный вариант декларативной регистрации slash-команд без ручного построения каждой команды в одном месте.

- `membercount.js` подтверждает TOM-148–149: до 25 динамических channel counters и большой набор placeholders; отдельный ID не нужен.
- `mute.js` в основном реализует TOM-157–158 и TOM-077: timeout/role mute, автоматическое снятие по времени и reminders; отдельной базовой механики не добавлено.
- `roster.js` в основном подтверждает TOM-160–161; обновление roster после изменения отслеживаемой роли рассматривается как runtime-деталь уже существующего Roster.
- `suggest.js` базово соответствует TOM-165–166; уникальные vote-switch и voter-list детали вынесены в TOM-239.
- `reactionrole.js` повторяет базовую reaction-role систему; проверка иерархии ролей и partial fetch считаются реализационными safeguards, не отдельной системой.
- `ranking.js` содержит большой legacy-командный слой; отдельными идеями выделены только анти-фарм и level-role reward. Остальные rank/leaderboard/XP mechanics уже представлены в банке.
- `clientvariables.js`, `events.js`, `erelahandler.js`, `slashCommands.js` и прочие loader/infrastructure handlers проверены; loader patterns, collections и базовый event registration не размножались, кроме декларативного slash builder TOM-240.
