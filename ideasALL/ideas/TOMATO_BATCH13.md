# Tomato6966 — Batch 13

Источник: `Tomato6966/Multipurpose-discord-bot`
Ветка: `new_2025`
Область: `events/client`, `events/guild`

## TOM-201 — Автоочистка несуществующих Bot Channels
Если в настройке списка bot-only каналов остались ID удалённых/недоступных каналов, при обработке команды бот проверяет их существование и удаляет невалидные ID из конфигурации.

## TOM-202 — Запрет обычных команд в Music Request Channel
Если для музыкальных запросов назначен отдельный канал, обычные команды в нём блокируются с коротким уведомлением, которое автоматически удаляется через несколько секунд. Это позволяет оставить канал исключительно под музыкальный request-интерфейс.

## TOM-203 — Предварительная проверка обязательных Bot Permissions
Перед обработкой prefix-команды бот проверяет наличие у самого себя необходимых Discord permissions (`Use External Emojis`, `Embed Links`, `Add Reactions`) и сразу сообщает пользователю, какой permission отсутствует.

## TOM-204 — Автовход бота в новые Threads
На событии создания thread бот автоматически присоединяется к нему, если thread допускает join и бот ещё не joined. Это можно использовать для автоматической работы event/listener-систем внутри новых threads.

## TOM-205 — Единый Command Gateway для Prefix и Slash
Оба способа вызова команды проходят через общий набор проверок: guild-only, bot-channel restrictions, cooldown, permissions, music/voice preconditions, статистику и затем исполнение команды. Это уменьшает расхождение поведения между prefix и slash версиями.

## TOM-206 — Synthetic Message Adapter для Slash Commands
Slash-команда передаётся в существующий command runner вместе с искусственно созданным объектом, похожим на `Message`: author, member, channel, guild, timestamps, attachments, embeds, components и т. д. Это позволяет переиспользовать message-oriented обработчики без полного дублирования логики.

## TOM-207 — Плейер/Node Self-Healing перед Music Command
Перед музыкальной командой проверяется состояние Lavalink/player node; если node отключён, бот пытается переподключить её. Если player существует без queue, он уничтожается с небольшой задержкой перед продолжением обработки.

## TOM-208 — Пакетные Music Preconditions
Музыкальная команда может декларативно требовать разные состояния через параметры: пользователь в voice channel, активный player, подключённый bot, предыдущий трек, тот же voice channel, DJ/song-requester check и т. п. Проверки выполняются централизованно до запуска команды.

## TOM-209 — Runtime Status с динамическими Placeholder'ами
Статус бота поддерживает шаблоны, вычисляемые во время работы: prefix, количество серверов, количество участников, дата/время создания бота, username/tag, число команд, использованные команды и сыгранные песни. Значения пересчитываются при каждой смене статуса.

## TOM-210 — Ротация нескольких Bot Status
Бот может автоматически переключаться между двумя настроенными status-текстами через фиксированный интервал. Дополнительно рекламный статус может временно подменять обычный статус внутри этого цикла.

## TOM-211 — Startup Runtime Diagnostic Table
При `ready` бот выводит структурированную runtime-сводку: bot user, число серверов, суммарное число участников, prefix, число команд, версии discord.js/Node.js, platform/architecture и потребление памяти heap/RSS.

## TOM-212 — Lazy Databasing для Setup-команд
Полная инициализация данных пользователя/сервера откладывается до фактического выполнения Setup-команды. Обычные команды используют базовую подготовку данных, а расширенная `databasing` запускается только там, где действительно нужна структура Setup.

## TOM-213 — Восстановление Partial Discord Objects перед обработкой
Перед обработкой сообщения бот при необходимости fetch'ит partial `channel` и partial `member`, чтобы основной command pipeline работал с полноценными объектами.

## TOM-214 — Очистка временных блокирующих ответов
Сообщения о неверном bot-channel, неизвестной команде, отсутствии permissions и некоторых других ошибках могут автоматически удаляться через несколько секунд, не засоряя рабочий канал.

## TOM-215 — Guild-only Guard для Interaction Pipeline
Центральный interaction handler отбрасывает DM-вызовы команд и возвращает пользователю явное ephemeral-сообщение о том, что конкретный interaction pipeline работает только внутри guild.

## TOM-216 — Отдельный Shard Lifecycle Logging
Для shard-событий можно отдельно логировать `ready`, `disconnect`, `error`, `reconnecting` и `resume`, не смешивая их с общими client lifecycle событиями. Это даёт диагностику состояния конкретного shard.

### Не добавлено отдельно
- `debug`, `error`, `disconnect`, `reconnecting`, `warn`, `rateLimit` client events сами по себе не считаются отдельными пользовательскими механиками — это базовые lifecycle/diagnostic hooks.
- `message.js` без логики и прочие пустые/почти пустые event handlers не добавлялись.
- Обычные cooldown/permission/unknown-command проверки не размножались как новые идеи там, где они уже представлены существующим банком; в этом батче сохранены только новые архитектурные варианты и конкретные дополнительные ограничения.
